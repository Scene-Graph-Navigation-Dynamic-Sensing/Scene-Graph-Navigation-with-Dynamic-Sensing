1. Where the batch method spent its time

The batch method (run_covis_update.py, already tuned from 667 s to 76 s) waits for the whole video, then runs every step in sequence. Three steps dominate: detection on the new video, relocalisation, and colored ICP.

4. The new structure: who does what, and where

The streaming engine is split by how long each piece takes. Anything slow runs in its own thread or process, so a keyframe never waits for it. Heavy Python on a thread had starved the keyframe loop through the GIL (keyframes up to 5.8 s late), which is why the graph builder became a process.

Keyframe loop

main thread · every keyframe
  • upload + edge-free mask ~1 ms
  • frame fit (occupancy lookup) <1 ms
  • evidence: hit / through / occluded on the GPU 4.7 ms
  • belief + co-visibility gate 2–4 ms
  • Chow labels, coverage, commit rule ~1 ms

Localizer

own thread · every 4th keyframe
  • 1 SuperPoint + 3 LightGlue pairs ~90 ms
  • memory features cached on disk
  • Sim3 refit over the last 24 keyframes

Detection worker

own process · only when needed
  • 6-keyframe windows around absent objects and new geometry
  • embed a track on first sight + every 5th frame
  • CLIP in batches of 32; in-process voxel map
  • due windows sent as one job

Graph builder

own process · when decisions change
  • only changed nodes rebuilt
  • footprints of unchanged objects cached 0.09 s
  • move rates learned at the end of the visit

5. When the answer is known

The batch method can only start once the video has ended. The streaming engine decides while the camera moves. This is the run on the idle server (one detection worker, before the graph cache).

7. Why the alignment changed

The batch method fits one rigid transform for the whole video, then corrects it with colored ICP (8 s). In a stream the camera's own trajectory drifts, so the fit moved 2–3 cm over the video. The test: how often objects that are really present look see-through (a symptom of misalignment; lower is better). A sliding window of 24 keyframes beat both the global fit and ICP, so ICP was dropped.

9. What is still slow

After the last keyframe the remaining wait is the last detection window: the project's own YOLOE + tracker + CLIP + fusion pipeline. It took 6–10 s per window on the idle server and 15–19 s when another user's job kept the GPU at 100%. Two attempts that did not help on a busy GPU: separate CUDA streams for detection and embedding (+7%), and two detection workers (the first window took 31.5 s instead of 15 s).

Not covered by these tests: the live depth model (177 ms per frame) and online SLAM. The replay used the recorded depth and poses, so on a real camera the keyframe rate will be set by depth estimation, not by this engine.
